## 1. Verdict in one paragraph

The Den is well-designed and honestly documented, and the newest code (Track E owner binding, enrollment, `code-brain-turn`, `private-fleet-enroll`, `BotsModel.swift`) is the best in the tree — the patterns to converge on already exist inside the repo. No rewrite is warranted anywhere. But the product has **one account-takeover-class hole that must be closed before any non-HJM member is allowed to register a regional server** (web hands every member's Supabase JWT to whichever volunteer server sorts first, and that server's WebSocket endpoint does not authenticate anyone), **a demo-blocking schema bug in the Track A work** (BYOK agents cannot be created at all), and **a cluster of honey-minting / double-spend paths in SQL** that are fine while the member base is trusted and are not fine after that. The efficiency picture is dominated by one habit — per-call `reqwest::Client` construction and 2–5 s polling loops on every surface — and by synchronous SQLite/disk work on the Swift main actor. Fix order is in §2; everything there is a small, local change.

## 3. Track A / bots / local hub (the active thread)

The stated safety posture **holds**: `executor.rs:207` still passes `Vec::new()` so an agent reply creates zero deliveries; owner is never taken from the caller over RPC (`bots.rs:1648,1677` and every `bots_*` arm); the listener refuses non-private binds (`transport.rs:85-105`, `private_fleet.rs:145-146`); foreign-owner denial is tested. Enrollment (domain-separated Ed25519, nonce + credential-hash + authority binding, replay table) is thorough. The one hole in the posture is §3.6.

### 3.1 [P0] Members' Supabase JWTs are handed to volunteer regional servers
`apps/web/lib/live.ts:21` picks `online[0]` from `hive_servers` and `:52` opens `…/live/<pid>?token=<session.access_token>`; `apps/web/app/projects/page.tsx:23-24` does the same for `/snapshot/latest`. `hive.servers()` orders by `region, display_name` (`20260912320000:95-99`), so a server named "AAA" in region "a" wins. Any member can pick the `regional_server` role at `/pair` (`apps/web/app/pair/page.tsx:18,152`) and `hive.server_register` accepts it (`20260913050000:65-87`). The server uses that token as a full bearer (`crates/hive-server/src/live.rs:99-100`, `member.rpc(&jwt, …)`). A hostile server therefore holds a token that can call `hive_fund_project`, `hive_member_key_set/remove`, `hive_invite_create`, `hive_member_update_profile` as that member for the token's lifetime. This is account takeover, and it also nullifies every RLS/visibility fix.
**Fix:** add `hive.live_token_mint(p_project_id)` (member RPC; HMAC of member_id+project_id+exp≤5 min under a hub secret) and a node-key-gated `hive.project_board_for(raw_key, member_id, project_id)` that applies `project_visible`. Interim, client-only: filter `pickServer`/`loadOverview` to `operator === 'hjm'` (the field is already returned).
**Test:** register a server as member B named "AAA"; as member A open a board; assert the server never receives a token that can call `hive_my_wallet` as A.

### 3.2 [P0] `/live/<pid>` never authenticates a subscriber, replays the last frame, and lets the joiner overwrite the room's credential
`live.rs:147` checks only `q.token.len() < 20`. `live.rs:66-72`: an existing room does `subscribers += 1; *room.jwt = jwt; return last`. `live.rs:159-160` sends `last` immediately. So a 20-character junk token on a public tunnel hostname returns the last board frame of any project with a legitimate viewer, and then poisons the room's polling JWT so every real subscriber gets `error` frames until someone reconnects. It also means the single shared JWT per room leaks private (`execution_mode='local'`) boards across members, and unbounded room creation with junk tokens turns one server into N×30 invalid-JWT hub RPCs/min.
**Fix:** validate on join (one `hive_is_member`/board RPC) before incrementing, replacing the JWT, or replaying; per-subscriber visibility check before `last`; cap rooms per server (~256); stop a poller after K consecutive errors.
**Test:** junk token against a room with an active subscriber → no frame, room JWT unchanged.

### 3.3 [P0 — demo blocker] BYOK agents cannot be created
`crates/ohhive-core/src/local_hub/bots_schema.sql:13-14` constrains `runtime_kind IN ('local','chatgpt_subscription','copilot_subscription','grok_subscription')`. `bots.rs:56-57` inserts `"anthropic_byok"` / `"nous_byok"` verbatim (`:425`), and `ohhive-ffi/src/bots.rs:407-439` `ensure_provider_agents` tries to create both whenever `member_key_status()` reports a key. No migration widens the CHECK (`mod.rs:119-161` stops at v10). Result: opening Bots as a member with an Anthropic/Nous key fails with "local database operation failed" every refresh, and the Track A acceptance test's "Anthropic-BYOK agent" cannot exist.
**Fix:** migration v11 rebuilding `agent_profiles` (SQLite cannot ALTER a CHECK — create-new/copy/drop/rename inside the existing tx, FK enforcement off), bump the `version > 10` guard.
**Test:** `bots_agents_create` round-trips every `AgentRuntimeKind` variant.

### 3.4 [P1] Turn context is the oldest 32 messages, not the most recent
`executor.rs:167-179` asks for `before: Some(incoming.server_sequence), limit: HISTORY_WINDOW`; `bots.rs:810-813` runs `… server_sequence < ?3 ORDER BY server_sequence ASC LIMIT ?4`. In any conversation longer than 32 messages the agent sees sequences 1..32 and never the thread it is replying to. Invisible in tests because none exceeds the window.
**Fix:** when `before` is set and `after` is not, select `ORDER BY server_sequence DESC LIMIT ?4` in a subquery and re-order ASC (or give `MessagePage` a direction).
**Test:** 40 messages, `before: 41, limit: 32` → sequences 9..40.

### 3.5 [P1] Delivery finish is generation-fenced but not status-fenced; a cancel can be reverted
`bots.rs:1329-1330` `UPDATE agent_deliveries … WHERE message_id=?1 AND recipient=?2 AND lease_generation=?6` has no `AND status='running'`; `bots_delivery_cancel` (`:1115-1117`) sets `cancelled` without bumping `lease_generation`; `executor.rs:146` on NoCapacity calls `bots_delivery_fail(key, lease, Some(retry_at))`. Sequence cancel → NoCapacity → fail writes `status='pending'` and the cancelled delivery is later re-claimed. `bots_delivery_complete(key, 0)` on a never-claimed row marks it `done`. This is exactly the mechanism the slice-4 human gate (`Held`) will rely on.
**Fix:** `AND status='running'` on the finish UPDATE; cancel bumps generation.
**Test:** claim → cancel → `fail(key, gen, Some(later))` returns `conflict`; a subsequent claim fails.

### 3.6 [P1] RPC lets any same-owner paired device post *as any of the owner's agents*
`transport.rs:145-152` (`bots_message_send`), also `:131,135,139`, take `actor` from the request; `bots.rs:1619-1628` `bots_actor` accepts `Principal::Agent(id)` whenever the agent's owner equals the node owner — no check that the calling node hosts that agent; `:1705-1729` then creates deliveries (`:914-920`). The FFI always hard-codes `Principal::User(self.owner)` (`ffi/bots.rs:260`), so this is RPC-only. It violates SIF design §5 and, more importantly, is an *existing* path that creates agent-authored messages with recipients outside the executor — i.e. it bypasses wherever slice 4's budget checks will live. Only tested for a foreign owner.
**Fix:** reject `Principal::Agent` unless `agent.preferred_host == self.node_id()`, or restrict RPC actors to `Principal::User(owner)` until Track E item 4.
**Test:** node B (same owner) sends with `actor: Agent(agent_hosted_on_A)` → `forbidden`.

### 3.7 [P1] Core storage has no input bounds; RPC accepts 8 MiB bodies and unbounded recipient lists
Bounds exist only in FFI (`ffi/bots.rs:221-227`: 64 KiB, 16 recipients; `:541` title 200). Core `bots_message_send` (`bots.rs:843-871`) checks only `client_request_id`; transport allows 8 MiB (`transport.rs:82`); `runner.rs:76` then fails any turn whose context exceeds 64 KiB. Each recipient costs two `Immediate` transactions (`:858-864`, `:1716-1719`). Move the FFI limits into `LocalHubStore::bots_message_send`/`bots_conversations_create`.

### 3.8 [P1] `client_request_id` namespace lets any poster suppress an agent's reply
Dedup is `(conversation_id, client_request_id)` regardless of author (`bots.rs:875-885`); the executor's key is `delivery:<msg>:<agent>` (`executor.rs:205`); `service.rs:96-97` promises `Conflict` on payload mismatch but it is not implemented. A member who sends any text with the executor's reserved key makes the agent's later send "succeed" by returning the human's message — delivery marked `done`, agent never replies. Scope idempotency by author (`UNIQUE(conversation_id, author_kind, author_id, client_request_id)`) and return `conflict` when author/body differ.

### 3.9 [P2] Smaller bots/local-hub items
`history_boundary` is stored (`bots_schema.sql:42`, `bots.rs:764-765`) but never enforced in `bots_messages_list`/`bots_conversation_search` — a later-joined agent's context includes pre-join history. Hot-path queries lack indexes: `agent_deliveries` is polled every 5 s per agent on `(recipient,status,…)` with only the `(message_id, recipient)` PK; `conversation_members` is looked up by `(principal_kind, principal_id)` but the PK leads with `conversation_id`. `bots_message_send` runs 5+N separate transactions with check-then-act gaps and a duplicate recipient aborts the whole send on the PK (`:914-919`). `mentions.rs:331-335` grants `@everyone` to agent authors (design says agents may not broadcast) and the `[A-Za-z0-9_-]` grammar cannot address agents whose names contain spaces/UTF-8, which `agents_create` accepts; nothing enforces per-owner case-insensitive name uniqueness. `MessageKind::System` still creates deliveries (slice 3 not landed). No causation/depth/`Held` columns exist yet — recommend making `message_send`'s delivery loop take a required `DeliveryCause` enum rather than an `Option` so the executor cannot accidentally pass "human". `ffi/bots.rs:325-342` `drain_once` rebuilds the runner and a fresh `reqwest::Client` every 5 s and runs SQLite on a tokio worker. `host` differs between community-paired (`:293`, reader node id) and private-fleet (`:310`, hub node id) sessions, so agents created in one mode never drain in the other. `executor.rs:93-96,116,128-150` swallows every storage error and resolves `policy_revision` by listing up to 1,000 conversations because `bots_conversation_get` is private. Archived agents can still join rooms/receive deliveries via RPC (`bots.rs:691-700,858-864`) and those deliveries never drain. NoCapacity requeue is unbounded (`executor.rs:45-47,143-147`). `rooms_create` is non-atomic (`ffi/bots.rs:548-551`). `runner.rs:83-85` builds the prompt with no participant names/kinds and interpolates `agent.name` raw into "You are {}" — fine for DMs, an injection surface once names carry into rooms. FFI/core agent-name limits disagree (256 vs 200). Structurally, `bots.rs` at 1,740 lines is three layers in one file with the 14-column `MessageRow` mapper copy-pasted four times (`:815-836, 924-948, 1153-1177, 1392-1424`); the DM rule ("recipient must be the coordinator") lives only in FFI so the same DM accepts different sends per entry point; `bots_conversation_search`, `bots_handoff_*`, `bots_delivery_cancel` are reachable from no surface and have no tests.

**State of the uncommitted Track A work.** Done and working: `mentions.rs` resolver (fences, inline code, escapes, ambiguity, self-mention, dedup, three tests); FFI `rooms_create`/`room_agents`/`mentions_resolve` with owner checks on every agent id; `send` widened to Team/Project with zero-recipient posts; `bots_room_agents` through core/LocalHub/RPC; `title` migration v10 with a test; the `human_group_chat_replies_once_and_then_stays_quiet` test asserting exactly two delivery rows after two drains. Blocking the demo: §3.3. Will produce off-topic replies in any room over 32 messages: §3.4. Preconditions for making slice 4 safe that are *not* slice-4 items: §3.5, §3.6, §3.8, System-message suppression. The `LocalHub` wrapper for `bots_conversations_create` (`bots.rs:1676-1686`) does not enforce the kind/project/title/member rules that FFI `rooms_create` enforces, so RPC-created rooms are less validated than UI-created ones.

## 4. SQL, RLS, honey (Supabase)

Every table has RLS; every credential that crosses a trust boundary is hashed; BYOK keys live in Vault; the ledger is append-only and balanced; the control-plane gateway (`ctl_pilot_call`, delegation credentials, TTL clamp) is well scoped. The problems are seams, not typos. Full effective-policy matrix in Appendix A.

### 4.1 [P1] No row locks around any balance check → double-spend / double-payout
`hive.fund_project` (`20260907234700:36-48`) reads `account_balance(wallet)` then posts with no `FOR UPDATE`; `hive.node_complete_card` (`20260913235718:33-63`) reads the lease and fund balance without locking either; `interview_poll` locks the session but not the wallet. Two concurrent `fund_project(100)` on a 100-balance wallet both pass; nightly `ledger_integrity` only reports it.
**Fix:** `perform 1 from hive.accounts where id = wallet for update;` at the top of every debiting function; lock the lease row in complete/checkpoint/release.
**Test:** two sessions race `fund_project`; second raises `insufficient_honey`.

### 4.2 [P1] Honey can be minted from the treasury by two independent paths; per-card payout is unbounded
(a) `hive.artifact_announce` (`20260905000016:68-83`) trusts `p_bytes`/`p_project_id` from any registered server; `settle_storage` (`20260905000019:44-76`) pays the server owner's wallet from the treasury for project-null replicas by self-reported bytes; the treasury is not in the negative-balance check (`0019:94`). (b) `ensure_interview_project()` tops the Interviews fund from the treasury whenever it drops below 20 (`20260905000014:80-87`, called from `20260912300000:63`); the fund pays the completing node on self-reported tokens; the member reimburses only inside `interview_poll` (`:92-99`), which they can simply never call — and a node reporting more tokens than the member holds makes `split_debit` raise and abort the poll, leaving `pending_card_id` set forever. (c) `20260913235718:44-47` `amt := least(amt, fund_balance)` — nothing ties `p_tokens_out` to the card's `max_tokens`, so one community completion drains an entire fund.
**Fix:** pay storage only for hashes announced as `kind='output'` by a node with an active lease (or `operator='hjm'`), cap bytes by `storage_gb_offered`, add treasury to the integrity check; reserve the interview reimbursement at `interview_send`; cap payout at `max_tokens × rate` and reject `p_tokens_out > max_tokens × 1.1`.

### 4.3 [P1] `node_fail_card` lets any node key block any card
`20260905000004:139-148`: `delete from hive.leases where card_id = … and node_id = nid` (may match nothing), then unconditionally `update hive.cards set status='blocked'` and inserts a `FAILED:` output; the cascade trigger (`20260907204830:98-102`) then blocks parents. Wrapper granted to `anon, authenticated`.
**Fix:** `if not found then raise exception 'no_lease_for_this_node'; end if;` (as `node_release_card` already does).

### 4.4 [P1] Coordinator snapshot and unanchored URL regexes leak/inject
`hive.snapshot_source` (`20260905000018:19-25`) selects every non-deleted project with title/goal/fund balance; `projects/page.tsx:23-31` prefers it over `hive_projects_overview`, so private (`execution_mode='local'`) projects are visible to all members — bypassing the 2026-09-13 visibility fix. Add `and p.execution_mode = 'hive'`. Separately, `bug_report_add_attachment` (`20260912280000:107`) and `custom_avatar_url` (`20260912240000:51`) check ownership with an **unanchored** regex, so `javascript:alert(1)//storage/v1/object/public/bug-attachments/<uid>/` passes and is rendered as `<a href>` (`requests/page.tsx:394`) / `<img src>` (`components/Avatar.tsx:350`, polled for every member every 20 s by `MembersSidebar.tsx:123`). Anchor with `^<supabase_url>/storage/…/<uid>/[^/?#]+$` or store the object path only.

### 4.5 [P1] Table-level policies are wrong; only the unexposed `hive` schema hides it
`20260905000001:247-251` grants `select` on all tables and `insert, update` on `members, nodes, regional_servers, projects, project_roles, cards` to `authenticated`, plus a default privilege. `members_self_update` (`:281`) has no column restriction → a suspended member sets `status='active'`, anyone sets `is_admin=true` (`20260912210000:13`). `projects_admin_update` (`:292-293`) lets an admin rewrite `owner_id`/`fund_account_id`/`deleted_at`. `nodes_owner_write` lets an owner set `role='regional_server'` directly. `hive.balances` (`20260906000029:83-86`) has no RLS and is granted to `authenticated`. 100+ `SECURITY DEFINER hive.*` functions were never revoked from PUBLIC, including `member_key_set_for/remove_for(p_member, …)` (`20260913223915:27-50` — overwrite/delete another member's BYOK key), `retire_old_backups(0)`, `clear_checkpoints`, `settle_storage`, `pair_sweep`. ADR-001 says the schema will be exposed by default; the day that toggle flips, all of this is live.
**Fix (one migration):** `alter default privileges in schema hive revoke execute on functions from public`; explicit `revoke all on all functions in schema hive from public, anon, authenticated`; re-grant the member-facing set; drop the blanket table insert/update grants (everything already goes through RPCs); column-restrict `members`/`projects` updates; add `project_visible` to `project_roles_member_read`; make `hive.balances` `security_invoker` or revoke it.
**Test:** pglite replay + `set role authenticated` + `update hive.members set is_admin = true where id = auth.uid()` must fail.

### 4.6 [P1] The migration set is not the source of truth and does not replay
`20260913221437:8` grants on `hive.notification_deliveries`, which no migration creates. `hive_presence_recent` (`web/app/page.tsx:54`), `hive_member_create_link_code` (`settings/page.tsx:371`), `hive_node_projects_overview` (`hub.rs:1469`) are called and defined nowhere. `20260913180000_code_session_create.sql:4-8` uses `hive.node_member_id`, first defined in `20260913223915` (sorts later). `20260914030000:1` ("PROPOSED ONLY… Do not apply") and `20260915120000:6-9` ("NOT YET APPLIED") sit in the applied directory; `docs/proposed-migrations/` does not exist. Several later files are non-idempotent (`20260912320000:35`, `20260914030000:3-49`, `20260915130000:3-14`). `public.private_fleets` (`20260915130000:3-15`) violates "never touch `public`" and `check-migrations.sh:20` only inspects `create table … hive.`.
**Fix:** `supabase db dump --schema hive` into a baseline migration; move or delete the two proposed files; renumber `20260913180000` after `223915`; move `private_fleets` into `hive`; add a CI step that replays every migration into pglite/postgres from scratch (`supabase/tests/*.sql` currently hard-code a production project UUID and are not in CI at all).

### 4.7 [P1] Two silent regressions from `create or replace`
(a) The local-mode no-ledger contract (`20260908030000:51-81`) was lost when `node_complete_card` was re-created in `20260913231336:206` and `20260913235718:23-75` without the `execution_mode` branch — a funded project switched to local now pays its owner's own node from its own fund. (b) The 50-honey welcome grant (`20260908000300:53-64`) was dropped when `invite_redeem` was replaced in `20260910000500:15-36`; `20260912290000:6-7` still describes it as live. Related: `hive_code_session_projects_node` is `language sql stable` (`20260915120000:132-137`) but transitively runs `UPDATE node_keys` via `verify_node_key` — the exact failure `20260907181751:1-8` documents; `hive card submit --project <title>` will fail once applied.

### 4.8 [P2] Smaller SQL items
`artifact_announce` writes caller-supplied `p_project_id/p_card_id/p_uploaded_by` (`0016:68-80`), so a server can attach artifacts to arbitrary projects and charge their funds at settlement. `pair_begin` (`0003:29-43`) is anon-callable with unbounded `p_hint` and no rate limit; `interview_send` re-copies the whole transcript into `cards.inputs` every turn with no `p_text` bound; `spawn_child_card` inputs and `personal_channel_post_node_event` payloads are unbounded. The ledger append-only trigger's hatch is a session GUC anyone can set (`20260906000029:51-57`); only the missing DELETE grant protects the table. `bug-attachments` and avatars are public buckets (`20260912280000:69-75`). Missing indexes on hot predicates/FKs: `leases(node_id)`, `ledger_entries(card_id)`, `(node_id)`, `card_outputs(node_id)`, `project_roles(member_id)`, `cards(parent_card_id)`, `checkpoints(node_id)`, `artifact_replicas(node_id)`, `notification_events(member_id, card_id)`. Ledger/backup numerics pass through `serde_json::Value` without `arbitrary_precision` (`hub.rs:1403`, `ledger_archive.rs:203`), so the "every digit survives" claim at `ledger_archive.rs:208-209` is untrue for >15-16 significant digits — and the archive *deletes* the hot rows. `ledger_archive.rs:189-191` deletes hot rows after `store.put` on the coordinator only; replication to factor 3 is an async 60 s pull, so a coordinator disk failure in that window loses a month of ledger.

## 5. Core runtime, FFI, native apps

### 5.1 [P1] Node key and vault key are exported into the process environment and inherited by children — including agent-run commands
`ohhive-ffi/src/lib.rs:518` `set_var("HIVE_NODE_KEY", …)` on pairing; `lib.rs:380,575`, `setup.rs:152,229`, `media.rs:73,129`, `server.rs:408` call `nodeconfig::export_env()` which `set_var`s every `HIVE_*` key (`nodeconfig.rs:52-72`); `local_hub.rs:277` sets `HIVE_VAULT_SELF_KEY` directly. Children spawned without `env_clear()`: `core/tunnel.rs:176-183` (cloudflared), `ffi/tunnel.rs:39-41` (`open`), `lib.rs:175` (`hostname`), and the LLM-driven `run_command_tool` at `coder.rs:834-840`. A card's agent — processing content authored by other members — can run `printenv` and exfiltrate the device credential when internet is allowed. Also: `set_var` from FFI threads races `getenv` on runtime threads (the reason Rust 2024 made it `unsafe`).
**Fix:** make `nodeconfig::load()` the only reader of the two secrets (drop them from `export_env`, never `set_var` them), keep an in-memory `RwLock<NodeConfig>` on `HiveNode`, and `.env_clear().envs(allowlist)` on every `Command`. Clippy `disallowed_methods` on `std::env::set_var` in `ohhive-ffi` as the guard.
**Test:** pair against a fake hub, then `run_command_tool("sh -c 'printenv HIVE_NODE_KEY'")` → empty.

### 5.2 [P1] A coordinator brain can mint child cards that bypass every `code_session_create` check
`coder.rs:1495-1505` passes `required_capabilities` verbatim to `hub.spawn_child_card`; `hive.spawn_child_card` (`20260907180447:71-74`) inserts it as-is, while the human front door (`20260913180000:38-53`) enforces absolute workspace, URL/ref regex, `max_turns ≤ 100`, cloud consent and provider-key checks. `CodeSessionSpec` docs (`coder.rs:147-181`) claim these fields are "never set by the running brain" — false once `coordinator: true`. Combined with `run_git` passing `url`/`ref` where git parses options (`coder.rs:528-530`, no `--`, no `-`-prefix rejection on the Rust side) and skill names/descriptions from a cloned repo's `.hive/skills/*/SKILL.md` being spliced into the **system prompt** (`coder.rs:938-943`), this is the path from "clone this repo" to "spawn cloud-brain children with `coordinator: true` on other nodes".
**Fix:** Rust-side validator mirroring `code_session_create` in the `spawn_card` arm for `modality == "code"` (child brain must be `local` unless parent was cloud, `coordinator: false`, `vault_name` equal to parent's); same checks in `hive.spawn_child_card`; `clone -- url`, reject `-`-prefixed url/ref, `GIT_TERMINAL_PROMPT=0`; move the skills block to the user turn inside an explicit untrusted-data envelope.

### 5.3 [P1] No-deadline paths that pin a worker forever
`llama_cpp.rs:35` `reqwest::Client::new()` with no timeout; `:376-388`/`:214-226` unbounded `send/json`; same in `whisper.rs:46`, `comfyui.rs:45`. `sandbox.rs:232-236` `call_run` has no wall-clock bound — fuel does not cover a guest blocked on host I/O. `coordinator_hub.rs:204-254` holds the token mutex across the whole HTTP call including up to 4 attempts × 10 s and `wait_ready`'s ~8 s of sleeps, so heartbeats through that transport wait behind a slow `claim_card`. And Sif #1's `tokio::join!` fix (`worker.rs:1180-1183`) runs both loops in **one task**, so synchronous calls on the dispatch path — `Component::from_file` (Cranelift compile, `sandbox.rs:226`), `remove_dir_all` (`:165`), up-to-512 MiB `std::fs::write` (`tools.rs:113-115`), `SkillStore::list` (`coder.rs:919`), `nvidia-smi` (`probe.rs:60,100`) — still stall the heartbeat; the regression test uses an async-sleeping backend and cannot catch it.
**Fix:** connect/total/idle timeouts on every backend client; `tokio::time::timeout(limits.wall_clock, call_run)`; hold the token lock only to read/compare-and-set; `tokio::spawn` the heartbeat loop (needs an `Arc<dyn Hub>` clone) and `spawn_blocking` the listed calls.

### 5.4 [P1] Data-loss and silent-corruption edges in the card loop
`worker.rs:996-1011` checkpoints only `if phase != Done` and then `complete_card(..).await?` — one 20 s hub timeout after 30 minutes of inference discards the result; same for a whole multi-turn coding session (`:769-777`). `LocalBrain` maps an unparseable tool-call JSON to `Value::Null` (`coder.rs:352-353`), `write_file` defaults `content` to `""` (`:1470-1474`), `finish_reason` is ignored (`llama_cpp.rs:397-409`), and the default `max_tokens` for a code card is 1,024 (`worker.rs:222-235,577`) — so any `write_file` over ~1 K tokens **overwrites the target file with nothing** and reports `bytes_written: 0` as success. `artifact_fetch` (`hub.rs:1208-1216`) never verifies the bytes against the requested SHA-256 (no `sha2` anywhere in the node), so a bad replica can substitute input to a sandboxed tool; `tools.rs:115` also joins the unvalidated hash into a path. `run_command_tool` (`coder.rs:877-884`) replaces all captured output with empty on drain-grace timeout and leaks the reader task. Critique "PASS" detection is `starts_with("PASS")` (`worker.rs:964-965`), so "Passive voice throughout…" ships the draft unrevised. `nodeconfig::set` (`nodeconfig.rs:152-157`) writes `node.env` non-atomically with a world-readable window; `hive work --poll 0` / `check-in --interval 0` panic (`main.rs:461,565`; `worker.rs:1156`).
**Fix:** checkpoint the final state before `complete_card` and retry with bounded backoff; parse failure → tool error, `finish_reason == "length"` → retryable error, default code `max_tokens ≥ 8192`, `write_file` rejects a missing `content`; hash-verify fetches and `^[0-9a-f]{64}$`-validate the hash; keep partial output in an `Arc<Mutex<Vec<u8>>>` and `abort()` the reader; exact-match `PASS`; temp-file + `mode(0o600)` + rename; `range(1..)` on the clap args.

### 5.5 [P1] Polling and client construction (the dominant efficiency cost)
`hub.rs:517-528,57-62` builds a new `reqwest::Client` (pool + TLS handshake) **per call**; every FFI method (`byok_keys.rs:237-244`, `channel.rs:64`, `chat.rs:81`, `release_notes.rs:125`, …) constructs one. `HiveStore.swift:109-138` refreshes every 5 s with no in-flight guard, and each `snapshot()` (`lib.rs:377-434`) does a `sysinfo` hardware probe, an Ollama `/api/tags`, a hub `node_summary`, and a private-fleet check — then `ServerView` (4 s), `PrivateFleetView` (5 s, `channelList(limit: 200)` full reload), `BotsModel` (2 s + 5 s), `ChatGPTSettingsView` (2 s) add their own loops on top. On the server, `snapshot.rs:210` still builds a fresh client per follower refresh and `lib.rs:287` builds a replication client with no timeout. The `hive-server` startup re-announces every held blob with one sequential RPC each **before** binding the listener (`lib.rs:169-181,211`) — 10k blobs ≈ 17 minutes registered-but-not-serving.
**Fix:** one `HubClient` cached on `HiveNode` keyed by `(hub_url, node_key)`; split `snapshot()` into a cheap local half (5 s) and a hub half (30–60 s or on `on_changed`); a single cancellable `refreshTask`; delete `ServerView`'s private loop; compare before assigning `posts`; bind first and batch-announce in a spawned task.

### 5.6 [P1] Both on-device chat engines recreate `LanguageModelSession` every send
`ChatEngine.swift:262` → `checkAvailability()` → `:218` `session = LanguageModelSession(...)` unconditionally; identical in `FeedbackAssistant.swift:77→:35`. The model never sees prior turns. For the Feedback Assistant that breaks its own "ask at most one clarifying question, never submit twice" instructions (`:41-46`) — the clarification answer arrives context-free and the tool submits to a public board with no confirmation step.
**Fix:** create the session once / when `nil`; rebuild only on availability transitions; show the drafted report as a card with a single Send.

### 5.7 [P1] Chat history is wiped on the first decode failure; in-flight replies land in the wrong session
`ChatSessionStore.swift:416-421` `try?`-decodes to `[]` on failure and the next auto-save (`ContentView.swift:111-113` → `createSession()` → `save()`) overwrites the file; `ChatSession` has non-optional fields with no `decodeIfPresent` defaults (`:368-393`), so any schema bump deletes every saved chat. `ChatView.swift:46-49,186`: switching sessions while "Thinking…" lets the reply `append` and `persistCurrentSession()` into whatever `currentSessionId` is now (`ChatEngine.swift:305-309`). Same `try?`-to-empty pattern in `KanbanStore.swift:61-66` in both apps.
**Fix:** rename the undecodable file to `.corrupt-<date>` and surface it; custom `init(from:)` with defaults; capture `target = currentSessionId` at send and route the reply by target.

### 5.8 [P2] Native/FFI items worth a pass

## 6. Build, CI, release, packaging

### 6.1 [P1] The shipped `hive-server` is not the configuration CI checks
`release.yml:37,39` builds `-p hive -p hive-server` in **one** cargo invocation; with resolver 2 that unifies `hive-core` features across both, so the release server links a `hive-core` compiled with wasmtime (`sandbox`), sysinfo, the inference backends, etc. The pi-footprint job (`ci.yml:35`) builds `-p hive-server` alone — a different graph. `hive-server/Cargo.toml:3` says "No inference backends, ever." and README says CI enforces it; neither is true for the artifact members download.
**Fix:** two invocations, plus `cargo tree -p hive-server --target aarch64-unknown-linux-musl -e normal | grep -E 'wasmtime|sysinfo|rusqlite|openssl' && exit 1` in the footprint job.

### 6.2 [P1] `control.rs` (and therefore `hive-coordinator`) is never compiled or tested in CI
`lib.rs:571-572` gates it behind non-default `control-pilot`; no job passes that feature; its six tests (`control.rs:499-601`: token forgery, expiry, scheduler gates) never run and clippy never sees the file. It also pulls `native-tls`→`openssl-sys`, a second TLS stack untested on musl. Add `cargo test/clippy -p hive-server --features control-pilot`; consider `tokio-postgres-rustls`.

### 6.3 [P2] Release/packaging hygiene
`install.sh:32,54-55` verifies the checksum only if the SHA256SUMS download happens to succeed (`|| true`), and SHA256SUMS comes from the same origin — transport integrity only; publish a detached signature. `service-mac.sh:33` falls back to `curl` of an unpinned `main`-branch plist with no checksum, under `sh` without `pipefail`. `packaging/cloudflared-hive.service:3` instructs `cloudflared-linux-amd64` for an ARM64 Pi; `release.yml:218` bundles cloudflared 2026.8.3 into the notarized app with no checksum. `rust-toolchain.toml` floats on `stable` while `rust-version = "1.95"` is never checked — releases are not reproducible across weeks. `backup-to-sql.py:31` says missing columns take defaults; `jsonb_populate_recordset` + `insert … select *` inserts explicit NULLs, so restore into a schema with a NOT-NULL-default column fails. Backup state-file write failure is swallowed (`backup.rs:90`), so with a read-only parent every 10-minute tick runs a full export→gzip→age→new pinned artifact all day; the 8 MiB / 20 s "plain RPC" bound (`hub.rs:32,47,558`) is also applied to `backup_export`, `ledger_archive_export`, `snapshot_source` and the live board — nightly backups will silently stop once the hub export outgrows 8 MiB, with no `/health` signal. `GET /a/<hash>` reads whole blobs into memory with sync I/O on the runtime (`lib.rs:495`, `store.rs:60`) and there is no storage quota at all (`main.rs:175`, `put_blob` `lib.rs:432-488`). The snapshot member cache is keyed by full JWT and never evicted (`snapshot.rs:162,253-257`); JWTs travel in query strings (`lib.rs:405`, `live.rs`). No ESLint config behind `next lint`; `@hive/schema` is a dependency of web and desktop and imported by neither; `execution_mode` is accepted by `create_project_from_plan` but missing from `project-plan.schema.json`; two ToS version strings (`pair/page.tsx:9` vs `lib/tos.ts:4`). `generate-image/index.ts:90` `btoa(String.fromCharCode(...buf))` will throw on multi-MB images; `interview/index.ts:422,510` accepts unbounded `messages` and echoes raw provider error bodies; `tauri.conf.json:28` `"csp": null` alongside a `chatgpt_account(action, binary)` command that spawns a caller-supplied path (`lib.rs:1082-1085`).

### 6.4 [P2] The Tauri app is dead weight; do not merge its `bots.rs`
CI runs `--workspace --exclude ohhive-desktop`, so nothing in `apps/desktop` is compiled or linted on any PR; release builds it only as a macOS DMG even though ADR-018 keeps Tauri "for Windows and Linux"; the Swift shell already covers Setup/Server/Tunnel/Bots. ## 8. Strengths worth preserving (do not "fix" these)

Trust boundaries are stated in code, not just ADRs (`coder.rs` module doc, `mcp.rs` "does not sandbox anything", `tools.rs` "host-trusted card data", `desktop/mod.rs` "authority never from model arguments"). Fail-closed defaults where they matter: `NetPolicy` requires both flags, `tools_level` re-checked at execution, `CoordinatorHub` refuses raw node keys and non-TLS origins, `desktop::Budget` reserves before I/O. `skills.rs` and `desktop/provider.rs` are models of bounded-input code. The `CodeBrain`/`Hub`/`Backend` seams are real — every P1 in §5 is fixable inside one module. Track E owner binding was implemented as specified (immutable `nodes.owner_member_id`, `LocalHub` overrides `draft.owner`). Enrollment crypto and its mismatched-scope tests. Delivery claim/complete generation fencing and `bots_delivery_cancel`'s single-transaction discipline (the model to copy into `message_send`). `mentions.rs` is pure, tested, and explicitly not authorization. `serve()` refusing wildcard/public binds; `client()` refusing plain HTTP off-LAN. 0600 DB/selection files with symlink and mode checks; no `Debug` on credential-bearing structs. Real HTTP round-trip tests. Every credential crossing a boundary is hashed; BYOK keys in Vault with `last4` only; the balanced `post_txn` ledger with append-only trigger, `source` buckets, nightly integrity and checkpointed archival — it needs locks and caps, not a redesign. The control-plane gateway and the `code-brain-turn`/`private-fleet-enroll` functions (bounded body reads, strict validators, no upstream echo, origin allowlist, domain-separated Ed25519). `safeAuthReturnPath` is correct. `BotsModel.swift` (generation tokens, idempotent retry ids, `.task(id:)` cancellation, a real fake-session harness) is the pattern the rest of the app should copy. Google connector fundamentals (PKCE S256, per-attempt state, loopback listener, system browser, Keychain `AfterFirstUnlock`). Content-addressed store with hash-validated paths; hash-verified server-to-server replication; pinned-by-SHA GitHub Actions with `permissions: contents: read`; three-OS Rust CI; `hive-coordinator` genuinely I/O-free and unit-tested.
