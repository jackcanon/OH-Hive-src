# ADR-022: Personal Hive — One Interface Across a Member's Own Fleet

**Status:** Proposed · **Date:** 2026-09-13 · **Deciders:** Jack Blair (owner), Loki (architect) · **Source:** this conversation, mid-turn during a feature survey of Hermes Agent (Nous Research) and Buzz (Block)

## Context

Jack's own words, stated directly rather than inferred: "I want hive to be the best place to work on a user's personal hive... I have 6 computers and I want to be able to control my personal hive and work on personal projects with my personal hive... I want this to be my one interface to control all of my personal local agents and cloud agents." This came up specifically because the team was mid-way through surveying Nous Research's Hermes Agent for features worth importing (persistent memory, shipped earlier this session; an MCP client for cards, queued as follow-on work) — and several Hermes features that survey rated as a weak fit against Hive's shared-marketplace framing turn out to be a strong fit once Hive is also meant to be a *personal* fleet control plane, not only a community compute market.

This is not a new idea introduced from nothing. Two earlier ADRs already point straight at it:

- **ADR-015** already named the goal in almost the same words: "Jack's own stated goal — one system to coordinate his local and cloud agents — is now the app's central design." It also already made the schema support multiple personal machines, not just one: `execution_mode = 'local'` cards can be claimed by *any* node owned by the project's own member (`hive.nodes.member_id = hive.projects.owner_id`), not only the machine that created the project. Six of a member's own paired computers can already all pick up that member's own local-mode work today, with no new column and no new RPC.
- **ADR-016** already established that a member's own fleet has none of the shared-marketplace's multi-party trust problem, and proposed hub-portability (community / personal cloud / fully local hub tiers) precisely so a member's own machines keep working together independent of the community project's fate.

So the honest architectural read is: the data model and the trust/economics story for "my own fleet, coordinated" are *already mostly decided* by ADR-015 and ADR-016. What's actually missing is the **interaction layer** — there is no surface today that lets a member address "my fleet" as one thing. Each paired node is a separate Setup/Node/Server tab in its own copy of the desktop app; `ChatEngine.swift`'s `NodeStatusTool` only ever reports on the one machine the app is running on; the newly-shipped persistent chat memory (member-scoped, not node-scoped) is the first piece of state that already spans a member's whole fleet without anyone designing it to. Hermes Agent's actual shape — one agent, reachable from many surfaces, coordinating many machines, with persistent memory and delegated subagents — is a close match for this gap, closer than it is to Hive's shared-marketplace side.

Jack separately asked that Buzz (Block/Jack Dorsey's "hive mind communication platform," released July 2026, `buzz.xyz`/`github.com/block/buzz` — not to be confused with the unrelated outbound-sales product at the literal domain `buzz.ai`; flagged here in case that naming needs confirming with Jack) be weighed alongside Hermes, since it's working the same general space from a third angle. Buzz's actual shape is different again from both Hermes and today's Hive: not one personal agent following a member everywhere (Hermes), and not a compute marketplace (Hive today) — a shared *team* workspace (channels, threads, DMs, voice, code review) where AI agents are first-class participants with their own persistent, portable, cryptographic (Nostr) identities and permissions, working alongside humans in the same room rather than being invoked and replying. It's agent-harness-agnostic (bring Claude Code, Codex, Goose, or a custom agent) and open source (Apache-2.0). The piece of Buzz most relevant to Personal Hive is its permissioned-agent-identity model, folded into S6 and the open questions below; Buzz's decentralized Nostr identity layer solves a cross-organization portability problem Hive's closed-loop, single-hub-per-tier model (ADR-016) doesn't have, so it is not proposed for adoption here.

## Decision

### 1. Name the tier: "Personal Hive"

A member's own paired nodes, addressed and coordinated as one system, is a named, explicit concept — **Personal Hive** — sitting between two things that already exist and are unchanged by this ADR:

- A single machine's local session (ADR-015's `execution_mode = 'local'` as experienced on one Mac today).
- The shared community marketplace (ADR-001/ADR-002, `execution_mode = 'hive'`).

This is **not a new schema mode**. It is the existing `execution_mode = 'local'` + "any node this member owns may claim it" rule, given a real interface. No new `execution_mode` value, no new ledger behavior — S1 of ADR-015 already covers the data model.

### 2. A fleet channel, not a single chat thread — decided in favor of Buzz's model, for receipts

**Decided (Jack, 2026-09-13): "I want to be able to see the receipts, so I think we take Buzz's channel model and run with it."** This settles the open question the original draft of this ADR left open (channel vs. a single 1:1 chat thread). The reasoning: a chat thread's model of "the assistant, from memory, tells you what happened" is a summary — it can be wrong, it can omit things, and it gives no fixed record to check later. A channel where each event is its own durable, timestamped post gives an actual audit trail: you can see, after the fact and independent of any model's summarization, exactly what ran, where, and when.

Concretely, Personal Hive gets a member-scoped channel (`hive.personal_channel_posts` or similar — naming TBD at build time), distinct from the per-project community forum (`hive.project_comments`, shipped this session) in one important way: the community forum's authors are always members (`author_id references hive.members`), while a Personal Hive channel needs a **non-human author** too — a paired node posting its own activity ("Odin: card `render-thumb-3` completed in 4.2s," "Vanaheim: server role started") the same way `HiveStore.activity`'s local-only Swift feed already renders events on-device today, except durable, shared across every one of the member's machines, and visible from any of them rather than trapped on the one machine that happened to be running when the event fired.

This deliberately reuses ADR-020's already-designed discipline (`hive.notification_events`: a durable, queryable table is the record, not a transient broadcast) rather than inventing a third event-durability pattern — the difference here is scope (one member's own fleet, not community-wide subscriptions) and that the channel is bidirectional: the member can also post into it (a message, an instruction), and `ChatEngine.swift`'s `NodeStatusTool` fleet-scoped sibling (reporting on all paired nodes, not just "this Mac") becomes one more kind of post into the same channel rather than a separate, ephemeral chat surface. An assistant's reply is itself a receipt: it's in the channel, timestamped, next to the automatic node-activity posts it may be describing.

The persistent chat memory shipped earlier this session (member-scoped `hive.chat_memories`, not node-scoped) stays the *recall* layer — small, bounded, curated facts injected into a conversation. The channel is the *record* layer — everything that actually happened, unbounded, never summarized away. They serve different purposes and this ADR keeps them separate rather than merging memory into the channel or vice versa.

### 3. Cross-machine delegation as a member-visible action

`spawn_child_card` and the sub-delegation pause/resume machinery (ADR-006, shipped this session) already let the coordinator fan work out across nodes internally. This ADR promotes that from purely-internal scheduling to a member-visible action for Personal Hive: a member can explicitly say "run this on \<node\>" or "split this across my fleet" from chat or the project board, and see where each piece actually ran. No new execution engine — this reuses the existing delegation primitives, pointed at a UI a member can drive on purpose.

### 4. MCP client tools are scoped to "my fleet," not just "this box"

Task #177 (already queued this session, Jack's security call already made: MCP tool access for cards is gated to `execution_mode = 'local'`, never a stranger's distributed work) is refined by this ADR: "local" for this purpose means **any node owned by the requesting member**, matching ADR-015 S1's existing claiming rule — not strictly the one machine a tool happens to be configured on. A GPU workstation's locally-configured tools (a local model server, a big filesystem, a database) become reachable from a Personal Hive chat session running on a laptop, the same way ADR-015 already lets any of a member's own nodes claim that member's own local-mode cards. The trust boundary Jack already set stays exactly as strict — never another member's funded work — it is simply drawn around the member's fleet instead of around one machine.

### 5. Reach it from anywhere via the existing messaging bridge plan

ADR-020 (Telegram/Discord/Slack bridge, currently Proposed; the Telegram account-linking half is already shipped) already anticipated fleet-shaped tools in its chat design (`fleetHealth()`, `projectStatus()`). Once fleet-aware chat (S2) exists, that bridge becomes, cheaply, "control my Personal Hive from my phone" — the specific capability that makes Hermes valuable to its users, and one Hive can get largely for the cost of a tool addition to a bridge that was already planned, not a new subsystem.

### 6. Lean into per-machine identity, short of a full Bot Mode subsystem

Paired nodes already have a display name and an avatar/hardware preset (`NodeAvatar`, shipped earlier this session). This ADR does not propose building Hermes' full Bot Mode (independently configured, independently promptable named agents) or Buzz's cryptographic per-agent identity, but does propose that fleet-aware chat (S2) and delegation (S3) surface a node by that same name and avatar consistently, so a member's six machines read as six named, differentiated things ("ask Odin," "Vanaheim is idle") rather than an undifferentiated pool — most of the felt benefit of both Bot Mode and Buzz's agent identities, none of the added subsystem. If S4's fleet-wide MCP scoping ever needs finer-grained control than "any of my own nodes," Buzz's model (each agent holds its own defined permissions, not just membership in a trusted group) is the natural next reference point — flagged as an open question below rather than adopted now.

## Consequences

### Positive
- Reuses, rather than replaces, two ADRs' worth of already-decided architecture (ADR-015's multi-node local claiming, ADR-016's fleet-independent hub portability) — this is substantially an interface and tool-scoping decision, not a new execution engine.
- Gives a second, concrete reason (beyond the shared marketplace) for a member to want more than one paired machine, which is good for the product independent of Office Hours' community traction.
- Directly reframes the Hermes-agent survey's priority order: fleet-aware chat, cross-machine delegation UI, and MCP-for-fleet become the natural next slice, rather than isolated features graded against the wrong comparison (a shared marketplace) the first time around.
- The persistent chat memory shipped just before this ADR turns out, by accident of being member-scoped, to already be Personal-Hive-shaped — a small preview that "member-scoped, not node-scoped" is the right default to keep applying.

### Negative
- "One interface to control everything" is a much bigger surface than any single feature shipped this session — this ADR sets direction, it does not by itself reduce the amount of UI/UX work required (a real fleet dashboard, not just a tool the chat model can call, is probably still needed eventually).
- Cross-machine delegation made member-visible raises expectations about latency and reliability ("I told it to run on Odin, why hasn't it started") that purely-internal coordinator scheduling never had to meet — a member will notice and be confused by an offline or busy target node in a way the coordinator's own retry logic currently absorbs silently.
- Widening MCP tool reachability from "this machine" to "my whole fleet" (S4) is a real increase in blast radius compared to the original single-machine framing, even though it never crosses into another member's work — a compromised or misconfigured node's MCP tools are now reachable fleet-wide, not box-only.

### Risks & mitigations
- **A member's fleet looks "controllable" before the interaction layer actually exists**, since the underlying schema already permits multi-node local claiming today. Mitigation: this ADR is explicit that S2–S6 are new interface/tool work, not already-shipped capability — nothing here should be described to Jack or to members as done until the corresponding tool/UI ships.
- **Cross-machine delegation UI (S3) surfaces failure modes the coordinator used to handle invisibly** (a target node offline, a card stuck). Mitigation: any member-facing "run this on \<node\>" action needs an honest status/failure display from day one, not just a happy-path demo — same discipline as this session's `friendlyError()` work for the web app.
- **MCP fleet-scoping (S4) is a bigger security surface than single-machine scoping.** Mitigation: enforce the "member's own fleet, never another member's work" check server-side (in whatever resolves a card's execution context), not only in the client UI — the same principle already applied to every node-key-resolution RPC this session.
- **This ADR could balloon into "rebuild Hermes inside Hive"** if every survey item gets pulled forward under the personal-fleet framing. Mitigation: S1–S6 above are the scoped slice; broader Hermes features (Skills System, full Bot Mode, browser automation, voice mode) stay in the original survey's backlog and need their own explicit go-ahead, not an automatic pass because this ADR exists.

## Open questions
- Does "run this on \<node\>" require the target node to be online and idle right now, or can it queue against an offline machine the way Hive-marketplace card claiming already tolerates? (Open — affects whether S3 needs new queueing UI or can reuse existing card-claim semantics as-is.)
- Does fleet-aware chat (S2) get a dedicated "Fleet" view/tab, or fold into the existing Node/Kanban tabs each paired machine's app already has? (Open — an interface decision, not started.)
- Should Personal Hive chat memory (S2) stay a single unified member-scoped blob (today's shipped design), or does fleet-awareness eventually want a lightweight per-node annotation ("this fact is about Odin specifically") layered on top? (Open — today's design is deliberately simple; revisit only if it proves limiting in practice.)
- How does a multi-node Personal Hive project interact with promotion-to-Hive (ADR-015 S3, still a whole-project, one-direction, owner-only action)? Does promotion need to say explicitly that a project which had been running across several of the member's own machines now runs on a stranger's single machine at a time? (Open — ADR-015 didn't anticipate multi-node local projects being common; this ADR makes them more likely.)
- Which of S2–S6 should actually be built next, relative to the still-open Tauri feature-parity work and the MCP-client task (#177) already queued? (Open — a sequencing call for Jack, not decided by this ADR.)
- Should each paired node (or each role a node plays — worker, regional server, chat assistant) eventually get its own explicit, scoped permission set in the style of Buzz's per-agent permissions, rather than the current implicit "any node this member owns" trust boundary? (Open — S4/S6 flag this as a future reference point, not a decision; today's node-key resolution is simpler and has been sufficient so far.)
- ~~Does a member-facing "channel" view make more sense than a single 1:1 chat thread?~~ **Decided 2026-09-13 — channel, for receipts (see S2).** The four follow-on questions this opened are now also decided:
  - **Post volume: everything.** Every card/job lifecycle event, server/worker start-stop, and pairing event becomes a channel post, no significance filtering in v1. Simplest to build (no threshold-scoring logic) and easiest to add filtering to later, once real fleet volume shows what's actually noisy — same "ship the honest simple version, tune later" instinct as most of this codebase's v1 scopes.
  - **Channel scope: one fleet-wide channel, filterable per node — this already gets Jack "both" views for free.** A single `hive.personal_channel_posts` table per member, each row tagged with which node (or `null` for a member-authored post) produced it, is simultaneously "the whole fleet at once" (no filter) and "just this one machine" (filter by `node_id`) — one schema, two views, not two schemas. No separate per-machine channel table needed.
  - **Swift's existing local activity feed: kept, not replaced.** `HiveStore.activity` stays exactly as it is — cheap, already works, no hub round-trip needed for on-device-only viewing of this machine's own events. The new durable channel is additive: the shared, cross-machine, cross-session record: `HiveStore.activity` becomes one more local *producer* into the new channel over time, not something this ADR immediately rips out.
  - **First surface: the web app.** Matches the "check it later, from anywhere" motivation directly, and can adapt the project forum's existing comment-thread UI pattern (`hive.project_comments`, shipped this session) rather than building fresh SwiftUI first. Swift gets a channel view once the schema and web UI prove out the shape.

## 2026-09-15 extension — named bots and DMs

Jack now explicitly requests a bots workspace with team chat and per-agent DMs. [ADR-035](ADR-035-bots-chat-and-agent-collaboration.md) extends section 6's earlier exclusion of full Bot Mode, and the earlier single-channel-only scope, with stable agent identities, project rooms, private DMs and bounded collaboration. The receipt-preservation decision remains. Existing Swift/web channel code is a partial foundation; a per-node filter is not a DM. [Design plan](../docs/SIF-BOTS-CHAT-DESIGN-2026-09-15.md). This is a proposed implementation extension, not a shipped-feature claim.
